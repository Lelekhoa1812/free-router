# API and routing contracts

This document records the gateway's public wire boundary and provider-specific constraints. OpenAI APIs evolve; the official references below and the pinned SDK used by the compatibility suite are the source of truth for each release.

Last reviewed: 11 November 2026.

## Authentication and common behavior

Every `/v1` endpoint takes `Authorization: Bearer sk-fr-…`. Dashboard cookies have no API authority. Client keys are random 256-bit secrets, shown once, and stored as keyed hashes. A key record carries scopes (`chat`, `responses`, `embeddings`, `decisions`), model restrictions (allowlist or `*`), Jev permission, expiry, and revocation state. A missing `models` field defaults to `*` when a key is created; an explicit empty allowlist is rejected at creation and denies every model on an existing record, including discovery and detail lookups. Public JSON is `no-store`; errors use an OpenAI-style `error` object, stable code, and request ID. Admission and request-record IDs are generated by the gateway; a caller-supplied `x-request-id` is never trusted for either. The API body reader enforces a 4 MiB limit.

`/v1/models` advertises enabled chat models and aliases to keys with `chat` or `responses` scope. Jev is omitted unless `?type=decision` is requested. Provider-qualified model IDs preserve the upstream namespace, such as `nvidia/z-ai/glm-5.3-flash` behind the `nvidia/` gateway namespace. An alias can select a different provider only before semantic output begins. A pinned model never silently changes.

Embedding models are a separate, explicit-model family. `GET /v1/models?type=embedding` requires the `embeddings` scope and returns only available embedding models permitted by that key. An unfiltered `GET /v1/models` includes chat models for `chat`-scoped keys and embeddings for `embeddings`-scoped keys; an embeddings-only key can therefore use model discovery without gaining Chat access. `GET /v1/models/{model}` applies the same family-specific scope check.

## Chat Completions

The canonical request is intentionally narrower than every OpenAI parameter. It accepts `model`, `messages`, `stream`, `stream_options.include_usage`, one of `max_tokens` or `max_completion_tokens`, `temperature`, `top_p`, `stop`, function `tools`, `tool_choice`, `parallel_tool_calls`, `response_format`, `reasoning_effort`, `user`, `prompt_cache_key`, and `store:false`. Unknown fields are errors. Chat resource storage, `n > 1`, deprecated function fields, audio, hosted tools, and paid service tiers are unsupported.

Input messages are sent in order. Image input is routed only to a profile certified for vision. Tools and strict schema requests are filtered against per-binding capability status. FreeRouter never executes client tools. Tool-call IDs and argument fragments are returned to the client for execution and continuation. Provider-specific structured-output support is not inferred from a provider model catalog flag; each binding needs a successful validation record before automatic routing should advertise it.

The gateway requests upstream streaming even for nonstreaming Chat responses, assembles the response when the client asked for JSON, and normalizes public model IDs, tool indices, finish reasons, and optional usage in SSE. A stream error is an SSE error and is never terminated as a successful `[DONE]` response. The gateway retries only before a response stream is returned; requests already sent to the client are never spliced with another model answer.

### Alias routing

- `fr-fast` — low-latency models with passed text probe
- `fr-code` — general software engineering; requires catalog context ≥200k tokens and passed text/tools/schema
- `fr-quality` — complex reasoning; high-capability models
- `fr-vision` — image understanding; only models with passed vision probe
- `fr-auto` — deterministic fallback by default (vision → `fr-vision`, high reasoning → `fr-quality`, low reasoning → `fr-fast`, else `fr-code`); optional Jev classifier opt-in (Settings → Jev routing, requires admin acknowledgement)

Alias order is preference, not a promise that every candidate can serve every request. At request time, the gateway removes candidates that are not ready, lack a passed text probe, have no healthy configured credential, or do not satisfy the request's verified tool, schema, reasoning, or vision requirements.

### Provider-specific behavior

- **Google AI Studio** — OpenAI-compatible endpoint. Preserve stable prefixes and Google continuation metadata. Tool streams can omit tool indices or use a misleading stop reason; stream normalization is required.
- **NVIDIA NIM** — OpenAI Chat Completions shape. Heavy models can have long time-to-first-token; upstream generation streams and gateway heartbeats are enabled. GLM-5.3-Flash spends output budget on reasoning; gateway sends `reasoning_effort: "low"` when caller leaves effort unspecified.
- **OpenRouter** — OpenAI chat shape. Can return a usage-bearing terminal chunk with duplicate finish information. Prompt-cache affinity and provider rate limits are distinct from per-key quota counters.
- **Mistral AI** — `https://api.mistral.ai/v1` with Bearer auth. Gateway requests streaming upstream and maps `max_completion_tokens` to `max_tokens`. Rejects `developer` role when both system and developer messages appear (cannot preserve precedence). Direct probes passed streaming, function calls, continuation, strict JSON Schema, and vision for Ministral 3 8B/14B.
- **Matilda (Maincode)** — OpenAI-compatible at `https://matilda.maincode.com/api/v1` with `mc_live_` Bearer key. Gateway requests upstream streaming, maps `model`, `messages`, output-token limits, `tools`, `tool_choice`, `parallel_tool_calls`, `response_format` (`json_object`/`json_schema`). Rejects sampling controls (`temperature`, `top_p`, `stop`) and `reasoning_effort` until verified. Request limits: 64 KiB body, 16,000 chars per message. Inline `image_url` returns HTTP 400 (unsupported).
- **ZenMux** — OpenAI-compatible at `https://zenmux.ai/api/v1` with Bearer auth. Chat via `POST /chat/completions`, discovery via `GET /models`.
- **OrcaRouter** — OpenAI-compatible at `https://api.orcarouter.ai/v1` with Bearer auth. Chat via `POST /chat/completions`, discovery via `GET /models`. Supports meta-routes (e.g. `orcarouter/free`).
- **TokenHarbor** — OpenAI-compatible at `https://tokenharbor.ai/v1` with Bearer auth. Chat via `POST /chat/completions`, discovery via `GET /models`. Not yet live-probed; seed model is experimental.

## Quota admission

Chat Completions and the authenticated Playground pass through a local quota ledger before upstream dispatch. The ledger is configured by server environment variables and is not a public API. `QUOTA_MODE=observe` records request and token counters without blocking; `enforce` rejects a request that would exceed a configured per-minute or provider-local-day window; `off` bypasses the ledger.

A local rejection is an HTTP 429 with code `quota_exhausted`, a bounded `Retry-After` computed from the exhausted window, and the usual `error` envelope. This code is distinct from an upstream provider 429, which uses the existing upstream classification and may surface as `rate_limit_exceeded`. A streamed request denied before dispatch receives an SSE error frame and no successful `[DONE]` frame.

Reservations are per dispatched attempt: alias fallback and credential rotation can consume more than one request-window entry. Token reservations are settled once from provider-reported usage when available, otherwise from visible content and tool arguments. Failed or cancelled attempts release their token reservation, while dispatched request counters remain conservative. The dashboard projection is `GET /api/admin/quota`, requires an admin session, and is `no-store`.

The configuration, provider group boundaries, defaults, and known limitations are in [QUOTA_ROUTING.md](QUOTA_ROUTING.md).

## Responses

Responses input is converted into canonical chat messages for the selected model. Supported inputs include text, standard role messages, function calls, and function-call outputs. `instructions` apply to the current turn. `previous_response_id` is owner-scoped, expires after 24 hours, and carries compressed AES-256-GCM encrypted state with authenticated owner/resource/version/expiry data. A valid parent can be read when `store:false`, but the new response is not persisted.

Stored responses can be retrieved, deleted, and listed through `/v1/responses/{id}/input_items`. Foreign, expired, and absent records return the same 404. `conversation`, background execution, automatic truncation, hosted tools, files, audio, WebSockets, and encrypted provider reasoning envelopes are unsupported. For `stream:true`, FreeRouter requests upstream Chat Completions streaming and translates text and tool deltas into Responses events as they arrive. It emits monotonically increasing sequence numbers, preserves output-item order, reports a token-limit finish as `response.incomplete`, and writes stored state before `response.completed`. If the upstream stream fails or required persistence fails after SSE begins, the terminal event is `response.failed`; a partial stream is never reported as completed. Full SDK event parity, reasoning envelopes, and broad live-provider certification remain release gates.

See OpenAI's [Responses guide](https://developers.openai.com/api/docs/guides/migrate-to-responses), [streaming event reference](https://developers.openai.com/api/reference/resources/responses/subresources/streaming-events), and [conversation state guide](https://developers.openai.com/api/docs/guides/conversation-state).

## Embeddings

`POST /v1/embeddings` requires the `embeddings` scope and an explicit concrete model ID from `GET /v1/models?type=embedding`. Embeddings never accept `fr-auto`, an LLM alias, or a model substitution: credential rotation stays within the selected model binding and an upstream failure returns an error. Embedding calls are non-streaming; `stream:true` is rejected because vectors are returned as one standard OpenAI `list` response. No input text or vector is written to operational request logs.

The gateway accepts `input` as one non-empty text string or an array of 1–64 non-empty text strings (up to 256,000 total characters), optional `dimensions`, `encoding_format` (`float` or `base64`), and a bounded `user` identifier. If present, `user` is transformed into a client-key-scoped hash before it reaches the provider. Unknown fields, token-ID arrays, image/audio inputs, and provider-specific parameters outside this listed contract are rejected. The initial v1 surface is text-only even for the verified multimodal Nemotron VL embedding profile. The request body is limited to 4 MiB and each model's approximate token limit applies.

`dimensions` must be inside the selected model's advertised supported range. Fixed-width models reject overrides to any other width. `input_type` is an explicit retrieval extension with `query` and `passage` values: it is required for NVIDIA NIM Nemotron 3/3.5 and Llama Nemotron VL profiles; OpenRouter's tested Nemotron endpoints accept it optionally; Google rejects it. Callers should use matching query and passage modes for retrieval/indexing pairs. FreeRouter preserves the provider's vector order and validates count, indices, finite values, and requested width. Upstream usage is returned when present; it is omitted when upstream telemetry is absent rather than fabricated.

The enabled inventory, exact IDs, dimensions, retrieval modes, dated live-call evidence, and official provider references are maintained in [EMBEDDINGS.md](EMBEDDINGS.md). Google and OpenRouter use their OpenAI-compatible embeddings endpoints; NVIDIA NIM uses `/v1/embeddings`. See [OpenAI embeddings](https://platform.openai.com/docs/api-reference/embeddings), [Google OpenAI compatibility](https://ai.google.dev/gemini-api/docs/openai), [NVIDIA Nemotron Embed API](https://docs.api.nvidia.com/nim/reference/nvidia-nemotron-3_5-embed-8b-infer), and [OpenRouter embeddings](https://openrouter.ai/docs/api/api-reference/embeddings/create-embeddings).

## Jev native and OpenAI Decisions

`POST /v1/systemone` preserves TypeSafe's native `model`, `state`, and named `questions` shape. It accepts `jev-latest` or `jev-preview` and passes the gateway client's key scope while using the server-side TypeSafe key upstream. Experimental assets and box questions are disabled. `GET /v1/systemone/models` discovers names for the authenticated account.

`POST /v1/decisions` accepts OpenAI's `input` plus an ordered `questions` array. Question names are optional and need not be unique; answers return in question order with `name: null` when the caller omitted one. Predicate instructions accept OpenAI text and JSON content parts, while image evidence is rejected because Jev images are not enabled. Predicate questions map to native `noul`; choice options map to opaque internal IDs and are converted back to the caller's original typed values, with unique string/boolean values enforced; score levels preserve order, require a `label`, and return the native fractional expected score. `prompt_cache_key`, `prompt_cache_options`, and `safety_identifier` are accepted for OpenAI compatibility and ignored because Jev exposes no equivalent control. Probability values and confidence remain separate, and `usage` carries the full OpenAI token shape. Responses omit `id` and `object` because OpenAI's Decision object has neither. Upstream failures are translated into the gateway's OpenAI-style `error` envelope. OpenAI defines no `stream` parameter for Decisions; `stream:true` is rejected because Jev cannot stream. Use `jev/jev-latest` or `jev/jev-preview` as the model name.

Jev routing is an internal option for `fr-auto` and never replaces the model answer. It is disabled by default, opt-in requires an administrator acknowledgement, the request excerpt is limited to 8,192 characters, and failures/low confidence fall back to deterministic routing. The gateway does not add credits or top up the TypeSafe account.

See [OpenAI Decisions](https://developers.openai.com/api/docs/guides/decisions), [TypeSafe System One](https://docs.typesafe.ai/api/system-one), and [TypeSafe model discovery](https://docs.typesafe.ai/api/list-models).

Unknown and experimental capabilities are excluded from automatic routing. At present the registry is a dated, checked-in snapshot; authenticated daily catalog discovery, complete probe workflows, capability retest management, and mutation-safe activation need further implementation.

- **Mistral AI** — `https://api.mistral.ai/v1` with Bearer auth. Gateway requests streaming upstream and maps `max_completion_tokens` to `max_tokens`. Rejects `developer` role when both system and developer messages appear. Direct probes passed streaming, function calls, continuation, strict JSON Schema, and vision for Ministral 3 8B/14B. See [Mistral's migration guide](https://docs.mistral.ai/resources/migration-guides) and [function calling](https://docs.mistral.ai/inference/conversations/function-calling).
- **TokenHarbor** — OpenAI-compatible at `https://tokenharbor.ai/v1` with Bearer auth (`TOKENHARBOR_API_KEY_1..9`). Chat via `POST /chat/completions`, discovery via `GET /models`. Gateway sends default OpenAI body (streaming upstream, `max_completion_tokens` mapped to `max_tokens`) with no provider-specific translation. Direct OpenAI SDK probes on 4 November 2026 passed model discovery, streaming chat, system/developer messages, JSON mode, strict JSON Schema, native streamed function calls, `parallel_tool_calls:false`, and tool continuation. Gateway routing and quota ledger support standard OpenAI payloads, meta-routes (e.g. `orcarouter/free`), and streaming SSE.

## Prompt caching and usage

There is no answer cache. Provider prompt/KV caching, gateway binding affinity, Responses state, and the short-lived Jev classifier cache are separate. Provider cache usage is reported only when an upstream supplies it; missing telemetry is unknown, not zero. Do not forward OpenAI-specific explicit cache fields to providers without a certified mapping. Google may use implicit prompt caching; OpenRouter supports provider-specific affinity; hosted NIM cache server settings do not apply to NVIDIA's hosted service.

Usage counts are returned only when the upstream reports them. The gateway does not fabricate token counts. Model catalog context/output values are advertised limits and do not supersede gateway safety limits or account-specific provider quota.
