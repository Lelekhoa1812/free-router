# FreeRouter operations guide

Last reviewed: 3 November 2026. Provider catalogs, access, free quotas, and deployed behavior change. Re-run the documented checks before enabling a model or claiming compatibility.

## Service layout

FreeRouter is a Node.js 24 Next.js application deployed to Vercel. `/v1` routes authenticate generated `sk-fr-` client keys and implement OpenAI-shaped model, Chat Completions, and Responses contracts. LLM calls use Google AI Studio, NVIDIA NIM, OpenRouter, or Matilda (Maincode) credentials encrypted at rest in the MongoDB `provider_credentials` collection. The dashboard manages slots, probes credentials before saving, and reads the current secret from MongoDB for each new request; provider secrets are never returned to browser code. TypeSafe Jev is available separately through its native System One endpoint and an OpenAI Decisions adapter. The optional Jev classifier runs only for `fr-auto` after an administrator enables it and acknowledges that a bounded request excerpt is sent to TypeSafe and uses existing account credits.

MongoDB is the only durable database. It stores client-key hashes, provider health and binding observations, request metadata, configuration, and encrypted Responses state. Upstash Redis coordinates request admission, in-flight leases, login throttling, daily Jev request budgets, short-lived classifier affinity, and the local quota ledger. Redis or MongoDB failure should be treated as an operational outage, not as a reason to skip authentication or quota checks.

## Environment setup

Use `.env.example` as the variable-name reference. Keep `.env` out of Git and configure only infrastructure and Jev secrets in server-only Vercel variables. Provider keys are added, replaced, paused, retested, and removed on the Providers page; each provider has nine numbered MongoDB slots, and slot number continues to define its independent quota group. The API tests each submitted key and stores it with AES-256-GCM encryption using `STATE_ENCRYPTION_KEY`. Missing slots are skipped. Provider key values are never returned to the browser or written to operational logs.

Required server settings are `MONGO_DB_CONNECTION_STRING`, `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `ADMIN_SESSION_SECRET`, `STATE_ENCRYPTION_KEY`, `CLIENT_KEY_HASH_SECRET`, and `CRON_SECRET`. `IMAP_HOST` and `IMAP_PORT` are optional and currently unused because FreeRouter sends mail but does not read the mailbox. `JEV_TYPESAFE_API_KEY` is needed for Jev endpoints and optional classification. `QUOTA_MODE` is optional and defaults to `observe`; `QUOTA_CONFIG_JSON` is optional and uses safe defaults when empty. Set `MONGODB_DB=freerouter` unless a different database name is intended. See [quota routing](QUOTA_ROUTING.md) before enabling enforcement. Use independent random values for the session, encryption, client-key hash, and cron secrets. During encryption-key rotation, configure the previous state key until records encrypted by it expire. Remove the obsolete `ADMIN_PASSWORD` Vercel variable after migrating to email-code access.

The dashboard login uses a shared random six-digit password and a signed 12-hour cookie bound to the current authentication epoch. While fewer than two recipient emails are registered, the login additionally requires a matching email; from two recipients onward, the login UI hides the email field and the password alone authenticates. In password-only mode, session identity is recorded as the shared operator rather than an email, so removing a recipient stops notifications but does not revoke that person’s access to the shared password. Rotating the password invalidates all prior sessions. This is deliberately shared access: anyone who knows the code can manage recipients and all dashboard controls. Passwords are AES-GCM encrypted in MongoDB and remain valid until rotated. If no access users exist, only a request from `SMTP_USER` can seed the first address; the app creates a code and emails it to that sender mailbox. The **Users** page adds/removes notification recipients and rotates the code. Adding an address sends it the current code. A rotation invalidates all active sessions, refreshes the initiating administrator’s session, and emails the new code to all recipients. Keep the code within the trusted group: it is shared, displayed in the Users dashboard, and has only one million possible values. Each sign-in atomically claims an attempt against both a per-IP window and a shared deployment-wide ceiling (five per IP and fifty total per fifteen minutes); email-plus-password mode also keeps a per-recipient limit. Email requests are throttled by IP and recipient. The request-code endpoint returns the same response for listed and unknown addresses. `SMTP_PASSWORD` should be a Gmail app password (spaces are stripped by the SMTP transport); never expose it in UI, logs, Git, or screenshots. Generated client keys are shown once; the database stores an HMAC hash and a display prefix. Revoke a key before deleting it. Provider API secrets are encrypted in MongoDB and are managed on the Providers page; environment variables are not used as a runtime fallback.

## Local development and checks

Use Node.js 24.x and pnpm:

```sh
pnpm install --frozen-lockfile
pnpm dev
pnpm typecheck
pnpm test
pnpm build
```

The `.nvmrc` and GitHub Actions workflow pin CI to Node 24. The local workspace used Node 26 during the initial implementation, which prints an engine warning; production and CI should use Node 24.

The UI is available at `http://localhost:3000`. Sign in, confirm MongoDB and Redis connectivity under Setup, inspect configured provider slots, then create a client API key. Provider-key retests check authentication/catalog access; they do not certify every model capability.

## Live model streaming smoke test

`pnpm smoke:models` makes one bounded streamed generation request for each model currently designated ready in `scripts/live-model-smoke.mjs`. It loads local `.env`, skips providers with no configured key, chooses the first configured key per provider, sends a tiny prompt with a 128-token ceiling, and checks for visible answer text plus a finish marker. It prints model IDs, credential slot numbers, status, latency, byte counts, and event field names; it never prints credentials or generated answer text. Set `SMOKE_MODEL_TIMEOUT_MS` to change the 120-second per-model deadline, or `SMOKE_MODEL_FILTER` to run a subset by model ID.

`pnpm smoke:matilda` separately checks Matilda `/models` discovery, a JSON chat completion, native OpenAI-style SSE, and strict `json_schema`. It requires `MATILDA_API_KEY_1` through `MATILDA_API_KEY_9` and never prints credentials or generated text. The local gateway path is certified; complete the deployed smoke before relying on Matilda in production.

A passing smoke test establishes only basic text generation over SSE. It does not certify tools, strict JSON Schema, vision, quota headroom, account independence, Cursor behavior, or long-context limits. Capability claims require the contract tests in [API_CONTRACTS.md](API_CONTRACTS.md) and release evidence described in [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md).

## Provider credential migration and management

Provider API keys are runtime data in MongoDB, not Vercel environment variables. The `provider_credentials` collection has one unique record per provider and slot. Each record contains a SHA-256 fingerprint for health joins, a nonsecret label, and an AES-256-GCM encrypted secret bound to its provider and slot with authenticated associated data. The app decrypts only on the server when routing a request. `STATE_ENCRYPTION_KEY` must remain available and must be backed up securely; preserve the current key as `PREVIOUS_STATE_ENCRYPTION_KEY` during a planned rotation until all records have been re-encrypted.

The one-time migration utility `scripts/migrate-provider-keys.mjs` reads numbered variables from local `.env` for OpenRouter, Google, NVIDIA, and Matilda, makes an authenticated catalog/key probe, and writes only HTTP 2xx credentials. A 401 credential is removed from Mongo only if the slot still contains that same fingerprint, so rerunning the migration cannot delete a newer dashboard replacement. Missing slots and inconclusive provider results are skipped. It prints only aggregate counts. After migration and deployment, remove `OPEN_ROUTER_API_KEY_1..9`, `GEMINI_API_KEY_1..9`, `NVIDIA_NIM_API_KEY_1..9`, and `MATILDA_API_KEY_1..9` from every Vercel environment; the app no longer reads these variables. Do not remove the encryption key.

On the Providers page, an administrator may add a key to an empty slot, replace an occupied slot, pause/resume it, retest authentication, or remove it. Saving checks the provider API before encryption and returns only health and HTTP status. Replacing a different key clears health and model-binding evidence associated with the old fingerprint. Removal deletes the encrypted record and related health/binding records immediately, so requests beginning after removal cannot select it. A key can be stored with `invalid`, `rate_limited`, or `unknown` health for administrative inspection, but routing skips invalid keys; retest after correcting access.

## OpenAI-compatible API

Set the OpenAI-compatible base URL to `https://<deployment>/v1` and supply the generated FreeRouter key as the Bearer token. `GET /v1/models` lists enabled LLM IDs and aliases. Namespaced concrete IDs include `google/<model>`, `nvidia/<model>`, and `openrouter/<model>`; aliases include `fr-fast`, `fr-code`, `fr-quality`, `fr-vision`, and `fr-auto`.

`POST /v1/chat/completions` accepts one choice and explicitly supported fields. Chat and Playground requests also pass through the local quota ledger; an enforced local rejection is HTTP 429 with code `quota_exhausted` and `Retry-After`, which is distinct from an upstream provider 429. The gateway always requests upstream LLM output with `stream: true`, including when a caller requests a normal JSON response. For caller streaming, FreeRouter opens SSE immediately and sends heartbeat comments while waiting for upstream headers and first content; it then normalizes and forwards answer/tool deltas. Provider reasoning-only fields are filtered from the public Chat stream. Alias fallback can happen before semantic output is sent, but responses are never spliced after visible answer/tool output. Strict JSON/schema/tool output is buffered and validated before release, with an 8 MiB cap. For a nonstreaming caller, the gateway assembles the streamed answer before returning JSON. Vercel’s maximum function duration remains a hard limit. NVIDIA GLM may have a long time to first content; it remains an available candidate only while actual response text and completion events are produced.

`POST /v1/responses` maps supported input, function tools, text formatting, and reasoning controls through the Chat adapter. With `stream:true`, the adapter requests upstream streaming and emits Responses text/tool deltas as they arrive. By default, it stores an encrypted, client-key-scoped continuation snapshot for 24 hours; it writes stored state before a successful terminal event. `store:false` does not create a new stored response. Stored responses support retrieve, delete, and input-item listing. Full SDK event parity, provider reasoning envelopes, and broad live-provider certification remain release gates.

Responses tool calls are returned for the client to execute. FreeRouter never invokes caller-defined tools. Chat resource storage, hosted tools, audio/video, background responses, and unsupported schema/provider options return explicit errors.

Cursor should use the deployment `/v1` URL, a generated key, and a custom model such as `fr-auto` or `fr-code`. Cursor's built-in Auto selection is separate from the FreeRouter alias. Verify a real agent/tool workflow on the deployed Cursor version before relying on it; SDK compatibility alone does not certify Cursor support.

## Jev APIs and credit policy

`POST /v1/systemone` proxies the TypeSafe native request and response shape. `GET /v1/systemone/models` and `GET /v1/models?type=decision` expose Jev model discovery. `POST /v1/decisions` translates OpenAI Decisions predicate, choice, and score questions to native System One and maps typed answers back. Jev does not stream; requests with `stream:true` are rejected. Jev calls use the supplied account and existing credits only. FreeRouter has no balance endpoint, does not add funds, and does not enable top-ups. An insufficient-credit result should be treated as a stop condition until an administrator explicitly retests.

The optional classifier is disabled by default. It consumes one Jev request when called, has a short deadline and daily local request budgets, and falls back to deterministic routing on low confidence or failure. It chooses a routing category, never the coding answer.

## Quota routing operations

The **Quota** dashboard shows operator-declared limits, assigned provider slots, live request/token counters, remaining headroom, resets, and configuration warnings. It is read-only; policy changes are environment operations.

Start in `QUOTA_MODE=observe` and let normal traffic populate at least one daily reset. Map each provider group to the real account or project boundary; Google keys from different projects must not share a group. Compare the dashboard with the provider console, enter current limits in `QUOTA_CONFIG_JSON`, then switch to `enforce`. Keep provider consoles as the final source of truth. A Redis outage allows observation traffic but fails closed in enforce mode. The ledger sees only gateway traffic, does not poll provider quota APIs, and has no durable reservation journal or Redis epoch recovery yet; see [quota routing](QUOTA_ROUTING.md) for the full contract and limitations.

## Health and model removal

The seed registry in `src/lib/models/catalog.ts` contains dated research and a `status` used to gate public model exposure. Models marked unavailable, restricted, or experimental are excluded from the concrete public model list and from aliases. Real upstream requests update credential and model-binding health. A 401 quarantines that credential; 404/retirement disables the affected binding; 429 and server errors create cooldowns. A failure in one account should not be treated as proof that the same model is unavailable in all independent accounts. An HTTP 503 also opens a provider/model-wide temporary overload breaker: first cooldown 30 seconds, then exponential backoff to a 5-minute cap for repeat failures within 10 minutes. The breaker is shared across all configured credentials for that exact model, and an active breaker removes the model from `/v1/models` and `/v1/models/{model}` without changing its permanent catalog status. Successful traffic after cooldown clears prior state unless a newer concurrent 503 has arrived. State expires after 15 minutes; no content or credential secret is stored in it.

NVIDIA GLM-5.3-Flash always spends part of its output budget on reasoning. NVIDIA documents maximum reasoning effort as the default and warns that a small `max_tokens` allowance may end with no answer text. FreeRouter therefore sends `reasoning_effort: "low"` for this model when the caller leaves effort unspecified; explicit caller settings are preserved. Smoke calls should allow at least 1,024 output tokens and check for answer content plus a finish marker. See [NVIDIA's GLM-5.3-Flash guide](https://docs.nvidia.com/nim/large-language-models/2.1.4/get-started/advanced/get-started-glm-5.3-flash.html).

After a repeatable live smoke failure, verify the exact provider model ID and rerun on another configured key before classifying the model as globally unavailable. Set its catalog status to `unavailable`, record the dated reason, and remove it from routing aliases. Do not treat a shared rate limit or provider outage as permanent model failure. Re-run type-check, tests, build, and model-list tests after catalog edits.

## Vercel deployment and rollback

Link the repository with the authenticated Vercel CLI or Vercel dashboard, select the `free-router` project, and use the Node.js 24 runtime. Configure Fluid Compute and the 300-second maximum duration where the Vercel plan permits it. Set production variables only in the Vercel project; isolate Preview from production credentials and data. The Vercel deployment should have MongoDB network access, Upstash access, and the required provider API egress.

The current Vercel Hobby deployment uses changing outbound IPs. The Atlas project therefore has a `0.0.0.0/0` IP access entry labelled `Vercel Hobby outbound IPs (FreeRouter)`. This admits connections from any IPv4 source; TLS and database authentication still apply. Remove this broad rule when moving to a deployment with stable egress, and replace it with the exact Vercel egress addresses. The current Atlas application user has the built-in `atlasAdmin` role across all resources, which is broader than FreeRouter needs. The app database is `freerouter`; reduce that user to `readWrite` on only `freerouter` (or create a dedicated least-privilege user and update the server-only connection string) before using this open network rule for sensitive production data.

`vercel.json` configures one daily maintenance cron. Protect `/api/cron/maintenance` with `Authorization: Bearer <CRON_SECRET>`. Cron cleans expired operational documents; the full storage pressure accounting and recovery controls described in the implementation plan are not complete yet.

Before production traffic, run CI and live model smoke tests, then run the deployed endpoint checks with an administrator-generated temporary key. Confirm the deployment URL, Node runtime, dependency readiness, model list, Chat streaming, Responses create/stream/retrieve/delete, Jev model discovery, native Jev and Decisions calls where credits permit, error/auth behavior, and Cursor acceptance. Revoke and delete temporary client keys after testing. Record request IDs and sanitized outcomes; never record secrets or prompt content.

For rollback, redeploy the prior known-good Vercel deployment and restore the matching application/catalog revision. Keep state encryption keys compatible with any stored response documents. Recheck health and `/v1/models` after rollback.

## Current operational limits

The first implementation still needs Redis epoch recovery and durable quota reconciliation, provider quota discovery, MongoDB byte reservations and pressure cleanup, temporary debug capture, complete admin audit/CSRF coverage, real integration and fault suites, Python SDK tests, accessibility/browser tests, and comprehensive Responses SDK/provider certification. The current dashboard is an operational starting point and does not yet provide the full charting, quota policy editing, and certification workflows in the product plan. These are explicit release gaps, not implied by the successful basic model smoke results.
